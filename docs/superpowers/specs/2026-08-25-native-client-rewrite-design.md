# Native Client Rewrite — Rust Core, Tauri Desktop, Swift iOS — Design

**Date:** 2026-08-25
**Status:** Approved (brainstorm), pending spec review
**Motivation:** The client stack is one Expo React Native codebase serving iOS *and*
desktop (via `react-native-web` inside Tauri). That single-source constraint is what
forces the two weakest structures in the repo: a `react-native-web` compatibility
layer under the desktop app, and **two terminal emulators** per platform
(`@xterm/headless` on the RN side owning state, xterm.js in a WebView owning
rendering) kept in sync by hand. Meanwhile ~18.8k lines of client logic — protocol,
replay, host store, session cache, git diff model — exist only in TypeScript, so any
native client would reimplement all of it.

Move that logic into a Rust core consumed by both clients: directly as a crate by the
Tauri desktop backend, and over UniFFI by a native SwiftUI iOS app.

## Goals

1. **One logic implementation.** Protocol, auth, replay, sessions, and the git model
   live in `tether-core` and are written once.
2. **One emulator per platform.** Desktop: xterm.js in the WebView, sole emulator.
   iOS: the core's parser, sole emulator. The shadow-copy sync problem is deleted, not
   managed.
3. **Delete `react-native-web`.** Once iOS is native Swift, the desktop frontend has no
   reason to be React Native.
4. **Native iOS.** A real SwiftUI app with real keyboard handling, replacing the
   WebView-in-RN terminal.
5. **A protocol worth keeping.** Binary frames, no base64 on the hot path, and TLS with
   certificate pinning.

## Non-goals

- **Android.** Dropped for now. Re-adding it means a third shell (Kotlin over the same
  UniFFI bindings — the core carries over, the UI is net-new).
- **A native macOS app.** Tauri covers macOS. A SwiftUI macOS target reusing `TetherKit`
  is a possible later phase, explicitly out of scope here.
- **Replacing the webview terminal on desktop.** Desktop stays a WebView app; this
  design removes the RN-web layer above it, not the WebView itself.
- **Server behavior changes.** PTY, holder lifecycle, auth model, and migrations keep
  their semantics. Only the wire format and transport change.
- **`wgpu` / GPU rendering.** Considered and rejected — see Decisions.

## Decisions (from brainstorm)

- **Desktop = Tauri 2, one codebase for macOS/Windows/Linux.** Its Rust backend links
  `tether-core` as a plain crate. **No FFI on desktop.**
- **iOS = SwiftUI, linking the same core** via UniFFI-generated Swift bindings packaged
  as an XCFramework. FFI exists in exactly one place.
- **iOS renderer = CoreText into a `UIView`,** drawing from the core's packed grid
  snapshots. Not `wgpu`: with desktop on xterm.js, a GPU surface would be
  written-once-used-once — pure risk for one platform. Monospace grid, no ligature
  problem, cheap and debuggable. Metal is a later optimization behind the same snapshot
  boundary.
- **Protocol v2 with protobuf.** Schema in `crates/tether-proto/schema/`, generated by
  `prost` (Rust) and `protobuf-es` (Bun). Only Rust and TypeScript ever touch the wire —
  Swift talks to the core, never to the server — so the schema needs two language
  targets, not four.
- **TLS + certificate pinning in v1,** folded into the existing TOFU pairing flow.
- **Terminal parser: `alacritty_terminal` now, `libghostty-vt` later.** libghostty-vt is
  the right long-term choice (Ghostty's battle-tested core, SIMD parsing, fuzz-tested)
  but its API is explicitly unstable: the Zig API is available for early testing, the C
  API is in progress, and a tagged stable release is targeted around October 2026.
  Pre-1.0 Zig + C ABI inside a Rust crate that must also cross-compile to
  `aarch64-apple-ios` is risk stacked on risk during the months of writing two clients.
  The core keeps terminal state behind a trait so the swap is contained.
- **v1 scope: hosts/pairing, session list + start/kill/rename, terminal with replay,
  push.** Git, files, upload, and presentations land in v2. The RN client keeps shipping
  until parity, so nothing regresses.

## Architecture

```
apps/server/          Bun+Hono. Protocol v2 + TLS. Behavior otherwise unchanged.
crates/
  tether-proto/       .proto schema → prost (Rust) + protobuf-es (TS)
  tether-core/        hosts, auth, ws, replay, sessions, git model,
                      terminal parser (iOS consumer only)
  tether-ffi/         UniFFI facade. iOS ONLY.
apps/desktop/         Tauri 2
  src-tauri/          Rust backend — links tether-core as a crate. No FFI.
  src/                Vite + React + xterm.js. Render + input only.
clients/apple/
  TetherKit/          Swift package over generated UniFFI bindings
  TetherIOS/          SwiftUI app + Notification Service Extension
apps/mobile/          Existing RN client. Frozen, then deleted at parity.
```

### Core ↔ shell boundary

Two channels, deliberately not one:

- **Events, pushed.** An async stream out of the core: connection state, session list
  changed, title, activity, exit, diff-available. Structural, low frequency. Surfaces as
  Tauri events on desktop and an `AsyncSequence` on iOS.
- **Grid, pulled.** The shell asks `snapshot(session, viewport)` when a `generation`
  counter has moved, and gets back **one packed byte buffer** — not a vector of cell
  structs. A 200×60 viewport is 12k cells; marshalling 12k structs per frame across
  UniFFI is the one place this design could plausibly be slow, and the packed buffer
  sidesteps it. The buffer is a fixed-stride cell array — codepoint, fg, bg, attribute
  bits — prefixed by dimensions, cursor position, and the `generation` value it reflects.
  `generation` increments on any change to the visible grid; the shell compares it
  against the last one it rendered and skips the call entirely when unchanged.

Streaming damage rectangles across the boundary is the obvious alternative and it is a
trap: the bookkeeping lands on the wrong side of the interface.

Only iOS pulls grid snapshots. On desktop the core forwards raw PTY bytes to the
frontend and xterm.js parses them — which is why desktop needs no parser in the core and
ends up with exactly one emulator.

### Shell-owned, never core

Secret storage (Keychain / Windows Credential Manager / libsecret), push registration
and the APNs extension, window chrome, and keyboard handling. The core declares a
`SecretStore` trait; each shell implements it against its platform's store, preserving
today's `tether_password_<hostId>` keying.

## Protocol v2

**Frames** are length-prefixed binary:

```
u8  kind
u32 len
[len bytes payload]
```

`kind=OUTPUT` carries **raw PTY bytes** — no base64, no protobuf wrapper on the hot
path, killing today's 33% inflation. Everything structural (title, activity, exit, diff,
session list) is a protobuf message.

**Replay** moves from a monotonic `sinceId` to an **opaque cursor** returned with each
batch. This decouples replay from `terminal_logs` row ids, so the log store can later
become a ring-buffer file or gain compaction without a client-visible break.

**HTTP stays REST.** Sessions, git, files, upload, and presentations keep their route
shapes with protobuf bodies. They are request/response and low frequency; moving them to
WS-RPC would be churn for no gain. Only the WS gateway changes character.

**The holder socket adopts the same framing.** Server ↔ holder is newline-delimited JSON
with base64 payloads today. Same length-prefixed frames, no base64, and the codec is now
shared with the client protocol — one implementation, one set of tests.

**Coexistence.** `/api/ws?proto=1` is today's JSON protocol, untouched, serving the
frozen RN client. `?proto=2` is binary, serving the new clients. Two codecs sit in front
of one set of domain handlers, and both live until `apps/mobile` is deleted.

### Transport security

Adding TLS while issuing new clients that must pin trust anyway costs a fraction of
retrofitting it into shipped apps. The server generates a self-signed certificate on
first run; the existing `GET /api/status` + `POST /api/setup` TOFU flow is extended to
pin the certificate fingerprint alongside the token. `tether-core` owns pinning, so both
shells inherit it.

This closes the standing gap where the wire is unencrypted on `0.0.0.0` with
`cors: '*'`, and the docs compensate by telling users to run behind Tailscale. After
this, the wire is safe even when they don't.

## Testing

- **Protocol conformance in CI.** Spawn the real Bun server, drive it from a Rust
  client, assert every frame kind round-trips. A schema drift between `prost` and
  `protobuf-es` becomes a build failure rather than a runtime mystery.
- **Port the VT golden-file tests.** `apps/mobile/src/terminalEngine.test.ts` and
  `terminalRendererProtocol.test.ts` encode real accumulated knowledge about wide
  characters, SGR, and OSC handling. They port to the core rather than being rewritten.
- **Core logic tests in Rust.** The pure modules being ported — `terminalSessionLogic.ts`,
  `diffModel.ts`, `hostStore`, `hostHealth` — already have tests that translate close to
  mechanically.
- **Shells get thin tests only.** UI-level smoke tests. All decision logic lives in the
  core, where it is testable without a PTY or a simulator.

## Phases

Each phase ends in something runnable, ordered so the riskiest unknowns resolve first.

**P0 — core spike.** `tether-core` with ws + replay only, linked into the *current*
Tauri backend, streaming one session to the existing xterm.js via Tauri events. Proves
the core boundary with zero new UI. Days, not weeks. Treat its outcome as a go/no-go.

**P1 — server v2.** Full `.proto` schema, `?proto=2` gateway, holder socket reframed,
TLS + fingerprint pinning in the pairing flow, conformance CI green. RN client untouched
and still green.

**P2 — core to the v1 feature line.** Multi-host store, auth + `SecretStore`, session
list/start/kill/rename, activity and title inference, replay cursor, resident-session
LRU. This is the port of `src/tether/*` and `terminalSessionLogic.ts`.

**P3 — desktop frontend rewrite.** Vite + React + xterm.js; `react-native-web`,
`desktop*.ts`, `windowControls.ts`, and the separate desktop-keys path deleted. Desktop
reaches parity and becomes the shipping desktop client. **This phase alone leaves the
project better off than today even if everything after it stopped.**

**P4 — iOS.** `tether-ffi` + UniFFI + XCFramework build wired into Xcode, `TetherKit`,
the SwiftUI app to v1 parity. Push and the NSE land last, with the notification crypto
pulled down into the core — an improvement on today, where it lives in Swift inside an
Expo config plugin.

**P5 — v2 features, then retire RN.** Git drawer/review/commit, file tree and viewer,
upload, presentations into the core and surfaced in both clients. `apps/mobile` is
deleted only once both shells cover it.

## Risks

1. **FFI grid throughput on iOS.** Mitigated by packed buffers plus a generation
   counter. If it still fails, the fallback is shared memory — not a second renderer.
2. **Rust-in-Xcode build.** Known-annoying, well-trodden, not novel. UniFFI generates
   the bindings, so no hand-written FFI headers.
3. **Dual-maintenance window.** Every v1 bug is fixed twice — once in RN, once in the
   core — for as long as P3 and P4 run. This is the real cost being bought, and it is
   why v1 scope stayed narrow.
4. **macOS ships the weaker terminal.** Tauri covers macOS, so Mac gets the WebView
   terminal — on the platform where users most notice terminal quality. Reversible: a
   macOS SwiftUI target added later reuses `TetherKit` wholesale.
5. **Cosmetic drift between the two renderers.** Fonts, cursor shape, and selection
   behavior will not look identical between desktop and iOS. Accepted.

## Sizing

This is a multi-month rewrite, not a refactor — though roughly a third of the
full-native alternative (per-OS shells in SwiftUI/WinUI/GTK4 plus a shared `wgpu`
renderer), which was scoped and rejected as too costly for the marginal gain. P0 is about
a week of real work and answers most of the open questions.
